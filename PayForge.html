Contexte

Sécuriser les tests
d'une application fintech

PayForge est une entreprise du secteur fintech. Le projet TOMSEN consiste à développer une application web desktop permettant la création de compte, l'authentification, la connexion aux API bancaires, la consultation des données bancaires et le suivi de consommation. Le projet est organisé sur 5 sprints répartis sur 4 mois, en méthode Agile.

J'interviens en tant que consultante en test au sein de l'équipe Agile, aux côtés d'Elsa (Product Owner, responsable de la définition et de la validation des besoins), d'Alice (développeuse responsable des livraisons) et de Quentin (bureau d'études, en copie).

Objectif qualité

100 % de validation sur les fonctionnalités critiques (authentification, pièces justificatives, interconnexions bancaires) et 85 % minimum sur les fonctionnalités de criticité moyenne (tableau de bord, conseiller virtuel).

Période

Campagne organisée sur 5 sprints, répartis sur 4 mois (80 jours ouvrés disponibles).

Stratégie de test

25 scénarios & 6 méthodes de test

Cas nominal & cas d'erreur

Pour chaque fonctionnalité, j'ai systématiquement prévu un cas nominal — comportement attendu avec des données valides — et des cas d'erreur pour vérifier la robustesse face à des données invalides, des services indisponibles ou des actions inattendues.

  • Priorisation selon la criticité définie dans les spécifications
  • Couverture renforcée sur l'authentification et les interconnexions bancaires

Non-régression & traçabilité

5 scénarios de non-régression sur les parcours critiques garantissent que les nouvelles évolutions n'impactent pas ce qui fonctionnait déjà. Chaque exigence TOM-x est reliée à au moins un scénario et un cas de test.

  • Tests manuels uniquement — pas d'historique de tests, délai contraint
  • Environnements sandbox exclusivement, jamais de vraies données bancaires

Revue des exigences

Les coquilles critiques

Majeure TOM-6

Champ "Prénom" typé numérique

Le champ est défini comme numérique dans les spécifications, alors qu'il doit être textuel.

Majeure TOM-6

Format de date incohérent

Le format JJ/MM.AAAA mélange deux séparateurs différents dans les spécifications.

Majeure TOM-6

Règle d'âge figée sur 2007

La règle d'âge est basée sur l'année 2007, qui deviendra incorrecte avec le temps et devrait être calculée dynamiquement.

Majeure TOM-7

Comportement manquant après "Enregistrer"

Aucun comportement n'est décrit après l'action "Enregistrer", ni dans les spécifications ni dans le prototype Figma.

Critique TOM-10

Incohérence HTTP / HTTPS

Les URLs fournies utilisent le protocole HTTP, en contradiction avec les exigences de sécurité HTTPS — critique sur une application bancaire.

Critique TOM-13

Même incohérence sur l'API transactions

L'API de consultation des transactions présente la même incohérence HTTP/HTTPS.

Majeure TOM-10/11

Incohérence de nommage API

Les données retournées par l'API et les libellés affichés dans l'application ne portent pas les mêmes noms.

Risques & préconisations

Anticiper les risques projet

Élevé

Absence d'historique de tests

Aucun patrimoine de tests existant sur lequel s'appuyer pour ce premier cycle.

Élevé

Manipulation de données bancaires sensibles

Les APIs exposent des données financières personnelles — usage exclusif des environnements sandbox recommandé.

Élevé

Incohérence HTTP / HTTPS

Les URLs fournies en HTTP contredisent les exigences de sécurité HTTPS attendues sur une application bancaire.

Moyen

Un projet partenaire doit être intégré à TOMSEN, mais ses spécifications restent à confirmer par Elsa.

Livrable opérationnel

56 cas de tests prêts à l'exécution

Structure (8 onglets)

  • Exigences — mapping TOM-ID / cas de tests
  • Cas de tests — référence complète des 56 CDT
  • Sprint 1 à Sprint 5 — onglets d'exécution
  • Non-régression — 18 cas critiques à rejouer

Contenu de chaque cas

  • Identifiant unique (CDT-001 à CDT-056)
  • Préconditions directes et indépendantes
  • Mode opératoire détaillé étape par étape
  • Résultat attendu, résultat obtenu, statut
  • Colonne commentaires pour tracer les anomalies

Statuts prévus

« À exécuter » pour les cas prêts. « Bloqué » pour les cas dont les préconditions dépendent de réponses encore en attente — notamment sur l'authentification double facteur et la biométrie.

Recul & analyse critique

Ce que j'aurais pu approfondir

Tests de performance

Non demandés par Elsa (aucune exigence de temps de réponse ou de charge définie), hors périmètre d'un premier cycle sans historique de tests, et incompatibles avec le budget temps de 19,25 jours déjà alloué aux tests fonctionnels.

Tests d'API automatisés

Écartés faute de patrimoine de tests existant et compte tenu du délai contraint ; les API bancaires ont été couvertes par des tests d'intégration manuels. Cette automatisation reste une évolution possible pour un prochain cycle, une fois l'application stabilisée.

Conclusion de la mission

3 livrables produits

Mission réalisée — Prête pour l'exécution des tests

La revue des exigences a permis d'identifier 7 coquilles et 31 questions avant le développement. La stratégie de test a défini les méthodes, les 25 scénarios et la couverture nécessaire sur 19,25 jours estimés. Le cahier de recette fournit un support opérationnel avec 56 cas de tests prêts à l'exécution.

Recommandations prioritaires :

  • Créer un référentiel de tests réutilisable dès le Sprint 1
  • N'utiliser que des environnements sandbox pour les données bancaires
  • Clarifier le protocole HTTPS avant les tests d'intégration
  • Corriger les incohérences de spécifications avant le développement
